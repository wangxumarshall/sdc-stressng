## 二、核心成果

### 1. 研究修正了问题定义（本轮最有价值的认知）

盘点发现：**不是“没有随机”（252 个 stressor 已用 PRNG），而是随机的形状与 SDC 物理机理错配**——

| 重灾区            | 现状（实证）                            | 后果                                                  |
| ----------------- | --------------------------------------- | ----------------------------------------------------- |
| memrate           | 11 处硬编码 0xaa（含 asm）              | 每秒百万次存储只见 1 种位模式                         |
| cpu-int/armcrypto | 锁死种子                                | **每台机器每次运行操作数位相同**                      |
| FP 全家           | 算术缩放合成                            | 指数/尾数强相关，边界位型永远采不到（命中概率 ~2⁻⁴⁰） |
| 地址空间          | 随机地址引擎 ≤17 页；大缓冲全部顺序触碰 | “多 GB 随机地址 + 校验”组合不存在                     |

### 2. 落地的新能力（9 patch）

**三个新组件**：
- **core-bitgen**（P1）：SDC 定向位模式生成器——位段扫掠（D4）、57 项边界字典+邻域抖动（D3，含 Meta 核 59 的 1.1^52/53 位型）、FP 位型直合成（指数/尾数独立）、互补翻转对（D2）、汉明定向
- **stress-operand-var**（P2）：模式字典跑真实计算路径（ALU/乘法器/除法/FMA）+ golden 重放比对 + 位级诊断
- **stress-addrspace**（P3）：7 个地址形状配方——多 GB 随机固定地址（52 位 VA span）、逐 VA 位扫掠（bit 0..51）、密集随机偏移、guard 洞、**malloc 大内存**（用户点名）、大规模错位、混合页序，全部带校验

**六处现有加固**：cpu/armcrypto 种子解锁（P5）、memrate 写模式选项（P4）、fma/vecfp 位型直合成（P6）、vm 密集随机偏移方法（P7）、atomic 操作数抖动（P8）、man+sdc-run 编排（P9）

### 3. 验证数据

- **P1 统计验证**：边界命中 100% vs 均匀基线 ~0（>10⁶ 倍提升）；64 位全覆盖；FP 指数分布 125424/124926/749650 = 精准 1/8:1/8:3/4
- **故障注入**（每个新组件都做了）：翻 1 位 → operand-var/addrspace/vm-rand-offset 全部立即抓获，页级/元素级定位
- **性能零回归**：memrate 四模式带宽 10-11 GB/s（噪声内）；operand-var 112.8 万 bogo/2s
- **兼容性**：gcc 12 + gcc 7.3（20.03 容器）双绿；所有新行为默认关闭或兼容旧值
- **CI**（run 35449398396 全绿）：`operand-var PASS 505,141 ops/s`、`addrspace PASS 0.67`（单 op = 一轮多 GB 配方）已进 15 镜像结果矩阵，每日 cron 自动覆盖

## 三、复盘

### 做对了什么

1. **先研究后动手**：两份盘点（30 路径操作数分类 A13/B5/C12/D1 + 8 个地址形状缺口）让“变异不足”从直觉变成可执行的 patch 清单，且避免了重复造轮子（sve2 已是逐轮重随机的正面案例）
2. **“模式字典 × 均匀随机”混合设计**：文献（R2 D2-D5）+ 盘点共同指向——纯均匀对位段覆盖差、纯固定走另一极端；混合生成器一次设计全库复用
3. **fill/verify 流同步纪律**：P3 的三个 bug（重复页/重叠 slice/碰撞窗口）全来自同一根因（重叠随机写入打乱流对齐），发现一次后全部用“无放回采样/预绘制偏移”统一修复；`stress_bitgen_skip` 的 8 字节粒度对齐也是这个纪律的产物
4. **故障注入验证习惯**：每个 VERIFY 组件都注入翻转验证“真的能抓”——verify 代码本身没被验证过等于没有
5. **本地容器先行**：gcc 7.3 兼容性在 20.03 容器一次验完，没有像 CI 迭代史（第 8-14 轮）那样在 runner 上反复试错

### 踩的坑（按教训排序）

1. **框架约定的 0 基/1 基分派**：operand-var 方法表照 1 基写，`methods[0]` 是 NULL 的 "all" → SIGSEGV；且错位分派让“通过”的 4 个方法实际在跑别人的代码——**测试通过 ≠ 测的是你以为的东西**
2. **verify oracle 与负载不分**：atomic 的 `&unshared` 操作序列是恒等式 oracle（~tmp-1==tmp），我把它也随机化 → verify 崩。**随机化压力路径时必须保住校验路径的确定性**
3. **写文件时的“边写边想”**：addrspace 第一稿写了 300 行废弃代码（三次重排 guarded-holes 的顺序）；教训是复杂 recipe 应先在纸上定“预绘制决策 → bitgen 流 → fill → verify”的统一骨架再动笔
4. **仓库宏名臆造**：`HAVE_MMAP` 不存在（上游不设门）、`MB` 应为 `STRESS_MB`、`shim_mmap` 不存在（直接 mmap）——**grep 上游惯例先于写代码**（这与第五轮 EBADF 的教训同源）
5. **工具链试探性修改的浪费**：memrate 第一次编辑写成了死代码当场回滚——大改动前先想清楚注入点，宁可 git checkout 重来

### 遗留与建议

1. **bandwalk 窗口参数（6-20 位、5 档密度）是文献推断值**——拿到 Kunpeng 920/950 实测位翻位段分布后应校准（方案审查时已标注为决策点 1）
2. **cache/l1cache/cacheline 数据值未随机化**（P8 有意跳过）：它们是 set/way 记账标签，随机化会破坏 stressor 自身校验——如需覆盖，要重新设计 tag 编码，工作量不小
3. **P3 的 pagemap 物理地址导向未做**（方案里的“按 PFN 模式导向分配”）：需要 root + pagemap 权限，目标机上验证更合适
4. **SDC 实战检验**：所有组件在正确性维度全绿，但“变异质量提升 SDC 检出率”的最终证据要等目标机（Kunpeng 950）上与 SDCShield 协同的真机长跑——建议下一轮做 sdc-run.sh 的真机回归，对比新旧版本在同样时长内的 golden 失配率
5. CI 每日运行将持续累积 15 镜像的操作数/地址覆盖数据，一周后可对比变异前后 stressor 的 bogo-ops 稳定性变化

**一句话总结**：把“随机撒点”升级成了“SDC 定向变异”——9 个 patch、3 个新组件、6 处加固，全部带校验、全部故障注入验证过、CI 15 镜像全绿；过程中抓出并修复了 5 个自己引入的 bug，其中 atomic 的 verify-oracle 破坏和 operand-var 的分派错位都是“测试看起来过了但测错了对象”的典型，值得记入长期教训。
